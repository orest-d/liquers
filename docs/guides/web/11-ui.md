# 11. User interfaces

PURPOSE: The reader can show Liquers results in a user interface, or knows where to look when JavaScript in the browser has none.

A page can always show a result itself: evaluate a query and put the value into the document.
This chapter is about the other way, the Liquers user interface, in which what you see *is* the
value of a query. A panel shows the result of a query, a button runs a query, and the
arrangement of panels is data. The same description runs in a desktop window, in a native
program, and in your page.

This part of Liquers is younger than the rest, and its interfaces will change more.

## 11.1 The model

A Liquers user interface is a tree of *elements*: panels, views, consoles. Each element has a
*handle*, a number by which the page and the commands refer to it, and usually a *source*, the
query whose value it shows.

An element is a value. A query can produce one, and the library has elements for the common
cases:

| Element | Made by | Shows |
|---|---|---|
| asset view | showing any query | the value of the query: text, a table, an error, and its status while it is computed |
| Markdown view | `ns-lui/markdown` | Markdown text, rendered |
| query console | `ns-lui/query_console` | a line to type a query in, and its result |
| layout | a UI spec (section 11.3) | a menu and child elements |

You can look at an element without mounting anything:

```js
import init, * as liquers from "https://orest-d.github.io/liquers/pkg/liquers-web/liquers_web.js";

await init();
await liquers.init();
liquers.registerCommand({ name: "notes", run: () => "# Title\n\nSome *text*." });

const element = await liquers.evaluate("notes/ns-lui/markdown");
assert(element instanceof liquers.UIElement);
assert.strictEqual(element.typeName, "MarkdownElement");
assert(element.renderHtml().includes("<h1>Title</h1>"));
element.free();
```

`renderHtml()` gives the markup of an element as text. That alone is useful: it is a way to
turn Markdown, or a table, into HTML with a query.

## 11.2 Mounting a user interface

`liquers.mountUI(container, options)` puts a user interface into an element of your page and
keeps it up to date. Give it the query whose value is the first element. This needs a page, so
the tests do not run it:

<!-- example: not run — mountUI needs an element of a page -->
```js
import init, * as liquers from "https://orest-d.github.io/liquers/pkg/liquers-web/liquers_web.js";

await init();
await liquers.init();
liquers.registerCommand({ name: "hello", run: () => "Hello" });

const ui = await liquers.mountUI(document.getElementById("app"), {
  query: "hello/q/ns-lui/query_console",
});

const subscription = ui.on("status", (e) => console.log(e.handle, e.status, e.error?.message));
const h = ui.show("commands_doc");          // a second element, showing the value of a query
ui.show("hello", h);                        // ... now showing another query instead
console.log(ui.elements());                 // [{ handle, parent, typeName, title, status }, ...]

subscription.dispose();
ui.dispose();                               // the container is emptied; ui.running is false
```

The query `hello/q/ns-lui/query_console` reads from the right: make a query console whose first
query is `hello`. The instruction `q` turns "the query so far" into a value instead of
evaluating it, so the console receives the query `hello`, not its result.

| Member of the mount | What it does |
|---|---|
| `ui.show(query, handle?)` | shows the value of a query in a new element, or in place of the element `handle`; returns the handle |
| `ui.submit(query, handle?)` | runs a query as a button of the element would, for its effect on the user interface |
| `ui.elements()` | the elements, each with its handle, parent, type, title and status |
| `ui.on("status", callback)` | calls back when the status of an element changes: `"processing"`, then `"ready"` or `"error"` with the error |
| `ui.dispose()` | removes the user interface and empties the container |

The elements carry class names that start with `lq-`, such as `lq-element`, `lq-text` and
`lq-error`, and a table is a `<table class="liquers-records">`. The module brings no style sheet,
so the user interface takes the look of your page, and you style those classes as you like.

## 11.3 A user interface as data

A layout with a menu is described by a *UI spec*, which is plain data with a YAML form. Pass it
as `{ spec }` in place of `{ query }`:

```yaml
menu:
  items:
  - !button
    label: Add a greeting
    action:
      query: "hello/q/ns-lui/add-child"
layout: vertical
init:
  - "hello/q/ns-lui/add-child"
```

Read the action from the right. `ns-lui/add-child` adds an element as a child of the element
that started the query, and what it adds is the query before it, `hello`, which the new element
shows. The queries under `init` run once, when the layout first appears. So the whole button is
data, and so is the dashboard it builds.

`ns-lui` has commands to add (`add-child`, `add-instead`, `add-before`, `add-after`), to
`remove`, to move through the tree (`parent`, `children`, `next`, `prev`, `first`, `last`,
`roots`) and to `activate` an element; section 11.7 lists them, and everything a spec may
contain. A command of yours that runs from a button can find out
which element it was run for: `context.element` is that element's handle (section 5.4).

The next example mounts this spec. So that it can run without a page, it uses `mountRenderer`
(section 11.5), which hands the element tree to your code instead of drawing it:

```js
import init, * as liquers from "https://orest-d.github.io/liquers/pkg/liquers-web/liquers_web.js";

await init();
await liquers.init();
liquers.registerCommand({ name: "hello", run: () => "Hello" });

const spec = `
menu:
  items:
  - !button
    label: Add a greeting
    action:
      query: "hello/q/ns-lui/add-child"
layout: vertical
init:
  - "hello/q/ns-lui/add-child"
`;
let tree;
const ui = await liquers.mountRenderer({ render(newTree) { tree = newTree; } }, { spec });

const [layout, greeting] = ui.elements();
assert.strictEqual(layout.typeName, "UISpecElement");
assert.strictEqual(greeting.parent, layout.handle);            // added by the init query
assert.strictEqual(greeting.status, "ready");
assert(tree.elements[greeting.handle].html.includes("Hello"));
assert(tree.elements[layout.handle].html.includes("Add a greeting"));   // the menu button
ui.dispose();
```

## 11.4 Elements of your own

`liquers.defineElement` adds a kind of element written in JavaScript. `render` turns the
element's *props*, its data, into markup. `onEvent` turns an event into new props.
`liquers.element(type, props)` makes one, which any command can return:

```js
import init, * as liquers from "https://orest-d.github.io/liquers/pkg/liquers-web/liquers_web.js";

await init();
await liquers.init();
liquers.defineElement({
  type: "gauge",
  render: (p) => `<span class="v">${p.value}%</span><button data-lq-event="inc">+</button>`,
  onEvent: (p, e) => (e.kind === "inc" ? { ...p, value: p.value + 1 } : undefined),
});
liquers.registerCommand({
  name: "gauge",
  arguments: [{ name: "v", type: "int" }],
  run: (v) => liquers.element("gauge", { value: v }),
});

const gauge = await liquers.evaluate("gauge-50");
assert.strictEqual(gauge.kind, "gauge");
assert.strictEqual(gauge.props.value, 50);
assert(gauge.renderHtml().includes('<span class="v">50%</span>'));
```

Mounted with `mountUI(app, { query: "gauge-50" })`, a click on the button sends the event `inc`
to that gauge only. `onEvent` receives the props and `{ handle, kind, fields }`, and the element
is drawn again with the props it returns; `undefined` keeps them. A control marked with
`data-lq-event="name"` sends the event of that name, and `fields` holds the values of the
element's form fields.

Props must be plain data. A function, a `Date` or a cycle is refused with a `conversion_error`.
That is what makes such an element a value like any other: it can be the result of a query, it
is kept, and a saved user interface holds its props.

Where each function runs matters:

- **`render`** runs while the user interface paints. Keep it a function of the props. `ui.show`
  throws there.
- **`onEvent`** runs with the user interface free, so it may call `ui.show` and `ui.submit`,
  except to replace its own element: return new props for that.
- **`mount(node, props)`**, when you give one, runs once the element's node is in the page: to
  draw on a canvas, start a timer, attach a charting library. Return a function to clean up. It
  runs when the node is replaced or removed, and when the mount is disposed.

<!-- example: not run — mount needs a page's document, and draw stands for the page's own drawing code -->
```js
liquers.defineElement({
  type: "spark",
  render: () => `<canvas width="80" height="20"></canvas>`,
  mount: (node, p) => {
    const timer = setInterval(() => draw(node.querySelector("canvas"), p), 1000);
    return () => clearInterval(timer);
  },
});
```

The markup `render` returns is inserted as HTML, like the markup of the library's elements. So
escape any text in it that comes from users or from data.

Defining a type again replaces it, and its elements are drawn again. `undefineElement(type)`
removes it, and its elements show a placeholder until the type is defined again.

## 11.5 Rendering the tree yourself

A page built with a framework of its own, React or Vue or anything else, may not want Liquers to
write into the document. `liquers.mountRenderer(renderer, options)` runs the same user interface
and, instead of drawing it, calls `renderer.render(tree, changes)` after every change:

```js
import init, * as liquers from "https://orest-d.github.io/liquers/pkg/liquers-web/liquers_web.js";

await init();
await liquers.init();
liquers.defineElement({
  type: "gauge",
  render: (p) => `<b>${p.value}</b>`,
  onEvent: (p) => ({ value: p.value + 1 }),
});
liquers.registerCommand({
  name: "gauge",
  arguments: [{ name: "v", type: "int" }],
  run: (v) => liquers.element("gauge", { value: v }),
});

let seen;
const shown = new Promise((resolve) => { seen = resolve; });
const ui = await liquers.mountRenderer({
  render(tree, changes) {
    // changes is "all" (draw everything) or [{ inserted }, { removed }, { replaced }, ...]
    const gauge = tree.elements[tree.roots[0]];
    if (gauge && gauge.props && gauge.props.value === 51) seen(gauge);
  },
}, { query: "gauge-50" });

ui.dispatchEvent(1, "inc");               // what a click on the gauge would send
const gauge = await shown;
assert.strictEqual(gauge.kind, "gauge");
assert(gauge.html.includes("<b>51</b>"));
ui.dispose();
```

Each element of the tree has its `handle`, `parent`, `children`, `typeName`, `title`, `status`
and `html`, its markup with its children included. An element you defined has its `kind` and
`props` too, so a framework can draw it with a component of its own and ignore the `html`.
Liquers does not see the page's markup here, so the renderer forwards the user's events with
`ui.dispatchEvent(handle, kind, fields)`.

## 11.6 Limits

- **A slow query freezes the user interface.** The page does not repaint while a query that the
  user interface started is being evaluated. Keep such queries short, or make their commands
  asynchronous and let slow work happen elsewhere (section 5.7).
- **Two user interfaces on one page share the environment**, and a keyboard shortcut of a menu
  that has no focus runs in both.
- **Elements you define show in the browser only**, not in the desktop user interface of a
  native program.
- **Markup is inserted as HTML.** A value shown by the library's elements is escaped; markup your
  own `render` returns is yours to escape.
