# 11. User interfaces

PURPOSE: The reader can hold a Liquers user interface from Python, follow what its elements do, and open it in a desktop window.

Liquers has a toolkit for user interfaces in which every view is the value of a query, so that
what a user looks at can be bookmarked, shared and restored. A panel shows the result of a query,
a button runs a query, and the arrangement of panels is data. From Python you hold such an
interface on your environment, drive it from your script, and, if you want, show it in a desktop
window.

## 11.1 A user interface without a window

`env.ui()` gives you a *UI model*: the tree of elements that a window or a browser page would
show, kept up to date in the background. You add an element by giving it a query, and the model
evaluates the query and keeps the result in the element.

```python
import liquers as lq

env = lq.Environment()

@env.command
def report() -> str:
    return "rows: 3"

with env.ui() as ui:
    handle = ui.show("report")          # a new element; its handle is a number
    assert ui.wait_idle(timeout=10)     # wait until nothing is left to evaluate
    [info] = ui.elements()
    print(info.handle, info.type_name, info.status)   # 1 AssetViewElement Ready
    print(ui.asset(handle).get())                      # rows: 3
env.shutdown()
```

`show` returns at once: the element evaluates while your script goes on. `wait_idle` waits until
every element has finished, and returns `False` if `timeout` seconds pass first. `elements()`
lists what the model holds, and `ui.asset(handle)` is the element's result, with its log and
progress, as chapter 6 describes for any query.

The `with` block disposes of the model at its end; `ui.dispose()` does the same, and
`env.shutdown()` disposes of every model of the environment. A disposed model refuses every call.

## 11.2 Following what the elements do

Subscribe to status changes with `ui.on("status", callback)`. Each event names the element and its
new status: `Processing` when an evaluation starts, `Ready` or `Error` when it ends.

```python
import liquers as lq

env = lq.Environment()

@env.command
def report() -> str:
    return "rows: 3"

with env.ui() as ui:
    seen = []
    with ui.on("status", lambda event: seen.append((event.handle, str(event.status)))):
        handle = ui.show("report")
        ui.wait_idle(timeout=10)
    assert seen == [(handle, "Processing"), (handle, "Ready")]
env.shutdown()
```

The subscription ends at the end of its `with` block, or when you call its `dispose()`.

Callbacks run only on a thread that asks for them, never at a random moment on a thread of
Liquers: in `wait_idle`, in `await ui.wait_idle_async()` on your event loop, or in
`ui.process_events()`, which delivers what has arrived and returns how many events that was. A
callback may call `show` or `submit` itself. A callback that raises is reported the way Python
reports errors it cannot raise anywhere (`sys.unraisablehook`), and the other callbacks still run.

A query that fails does not raise. Its element shows the error, and the status event says `Error`
and carries the exception as `event.error`. A query that cannot be parsed raises `lq.ParseError`
from `show` at once.

## 11.3 Elements and actions

`show(query, handle)` gives an existing element a new query. If the old one is still running, its
result is thrown away when it arrives, so the element always ends with the query you gave it
last.

`submit(query, handle)` runs a query the way a button of that element would. The command knows
which element it acts for from its context:

```python
import liquers as lq

env = lq.Environment()

@env.command
def report() -> str:
    return "rows: 3"

@env.command
def refresh(state, context) -> str:
    return f"refreshed element {context.element}"

with env.ui() as ui:
    handle = ui.show("report")
    ui.submit("refresh", handle)
    assert ui.wait_idle(timeout=10)
env.shutdown()
```

Outside a user interface, `context.element` is `None`. Do not call `wait_idle` from inside such a
command: the model is waiting for that very command, so the call raises instead of waiting
forever.

The library's own elements are commands of the `lui` namespace. `ns-lui/query_console` is a
console for typing queries, and `ns-lui/ui_spec` builds a layout of menus and panels from a YAML
description. Their values reach Python as `lq.UIElement` objects, with a `type_name` and a
`title`. A command may return one, and `show` displays it. An element is a live object, not data,
so it cannot be stored.

## 11.4 Opening a window

`ui.run()` shows the model in the Liquers desktop window and returns when the window is closed.
This continues the first example and needs a display, so the tests do not run it:

```python
ui = env.ui()
ui.show("hello/q/ns-lui/query_console")   # the query console; type `report` into it
ui.run(title="Reports", size=(900, 700))
```

Call `run` on the main thread of your program: desktop windows must live there on some systems,
so Liquers requires it everywhere, and `run` raises `lq.LiquersError` on any other thread. While
it blocks, your commands keep running on other threads, and status callbacks run on the main
thread between frames.

The window closes when the user closes it, when a *Quit* menu item fires, when you call
`ui.close()` from any thread, or when the model is disposed. Ctrl-C in the terminal closes it too,
and `run` then raises `KeyboardInterrupt`. `ui.window_open` tells you whether it is showing. After
the window closes the model goes on, and `run` can open it again.

A server started with `env.serve()` (chapter 12) before `run` serves the same environment beside
the window, so a result computed for one is reused by the other:

```python
with env.serve(port=8080):   # in the background
    ui.run()                 # the browser and the window share the results
```

Every wheel of `liquers-py` can open the window. On a machine without a display the package
imports and the model works; only `run` fails. A package built from source without its `gui`
feature has no window, and `run` says so (chapter 2).

## 11.5 Elsewhere

- **In a notebook**, the values a query returns are ordinary Python objects, and the notebook
  shows them as it shows any other: a `polars.DataFrame`, the `view.to_pandas()` of a record
  view, a PIL image. A rendered template (chapter 10) can be shown as Markdown or HTML.
- **In a web page**, Liquers runs in the browser itself, and a page can also call a Liquers
  server. See [chapter 11 of *Liquers for the Web*](../web/11-ui.md).
- **In a desktop application written in Rust**, see
  [chapter 11 of *Liquers for Rust*](../rust/11-ui.md).

The queries are the same everywhere. A query that you developed in Python can be given to a web
page or to a desktop application unchanged, provided the commands it uses are registered there.

Elements cannot be written in Python yet. A slow query submitted as an action holds up the
model's other work, and freezes an open window, until it ends; keep actions short and let the
elements do the slow work.
