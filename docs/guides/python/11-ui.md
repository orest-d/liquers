# 11. User interfaces

PURPOSE: The reader can build a Liquers user interface from Python out of a UI spec, open it in a desktop window, and drive and follow it from code.

Liquers has a user interface in which every view is the value of a query, so that what a user
looks at can be bookmarked, shared and restored. A panel shows the result of a query, a button
runs a query, and the arrangement of panels is data. From Python you describe such an interface,
open it in a desktop window, and, when you need to, drive it from your script.

This chapter starts with a complete small application. The sections after it take its parts
one by one.

## 11.1 A first application

A window with a menu, a table, and a console for trying queries:

```python
# needs a display
import liquers as lq

env = lq.Environment()
env.store.set("data/sales.csv", b"region,month,amount\nEU,jan,120\nUS,jan,80\nEU,feb,95\n")

@env.first_command
def dashboard() -> str:
    return """
menu:
  items:
  - !menu
    label: Sales
    items:
    - !button
      label: All sales
      action: "-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child"
    - !button
      label: Europe only
      action: "-R/data/sales.csv/-/ns-rec/to_record/eq-region-EU/q/ns-lui/add-child"
    - !separator
    - !button
      label: Quit
      shortcut: Ctrl+Q
      action: quit
  - !button
    label: Console
    action: "ns-lui/query_console/add-child"
layout: vertical
init:
  - "-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child"
"""

ui = env.ui()
ui.show("dashboard/ns-lui/ui_spec")
ui.run(title="Sales", size=(900, 700))      # returns when the window is closed
env.shutdown()
```

Run it, and a window opens that shows the sales table. The menu *Sales* adds the whole table or
the European rows as further panels, and *Console* adds a line in which you can type any query
and see its result.

Three things made this application, and none of them draws anything:

- **The data and the commands** are the environment, as in every other chapter. Here it is one
  file in the store and the record commands of the library.
- **The description** is the text that `dashboard` returns, a *UI spec*. It names a menu, a
  layout, and the queries that fill them. `ns-lui/ui_spec` turns that text into an *element*, a piece of the interface.
- **The window** is two calls: `env.ui()` makes the interface, and `ui.run()` shows it.

Everything the user sees is the value of a query. The table is
`-R/data/sales.csv/-/ns-rec/to_record`; the button *Europe only* shows
`…/to_record/eq-region-EU`. To give the application another view, you write a command and add
one menu item whose action names it.

## 11.2 Describing the interface: the UI spec

Read an action of the menu from the right:

```text
-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child
```

`ns-lui/add-child` adds a panel to the layout that owns the menu. What it adds is the query
before it. The instruction `q` turns "the query so far" into a value instead of evaluating it,
so the new panel receives the query `-R/data/sales.csv/-/ns-rec/to_record` and shows its
result: first the progress, then the table, or the error if the query fails. The action of
*Console* has no `q`: `ns-lui/query_console` makes an element, and `add-child` adds that
element as it is.

The queries under `init` run once, when the layout first appears. They are how a spec says what
is on the screen at the start.

A spec is text, so it can come from anywhere a query can reach. The example returns it from a
command, which keeps the program in one file. In an application you would rather keep it in the
store, as `ui/dashboard.yaml`, and show it with `-R/ui/dashboard.yaml/-/ns-lui/ui_spec`; then the
interface can be changed without touching the program, and one spec can open another.

Section 11.7 lists everything a spec may contain: menus and submenus, shortcuts, the layouts
(side by side, stacked, a grid, tabs, windows), and all commands of `ns-lui`.

## 11.3 The window

`env.ui()` gives you a *UI model*: the tree of elements that a window shows, kept up to
date in the background. `ui.show(query)` puts the value of a query into it, and `ui.run()` shows
the model in the Liquers desktop window and returns when the window is closed.

Call `run` on the main thread of your program: desktop windows must live there on some systems,
so Liquers requires it everywhere, and `run` raises `lq.LiquersError` on any other thread. While
it blocks, your commands keep running on other threads, and status callbacks run on the main
thread between frames.

The window closes when the user closes it, when a *Quit* menu item fires, when you call
`ui.close()` from any thread, or when the model is disposed. Ctrl-C in the terminal closes it too,
and `run` then raises `KeyboardInterrupt`. `ui.window_open` tells you whether it is showing. After
the window closes the model goes on, and `run` can open it again.

A server started with `env.serve()` (chapter 12) before `run` serves the same environment beside
the window, so a result computed for one is reused by the other:

```python
with env.serve(port=8080):   # in the background
    ui.run()                 # the browser and the window share the results
```

Every wheel of `liquers-py` can open the window. On a machine without a display the package
imports and the model works; only `run` fails. A package built from source without its `gui`
feature has no window, and `run` says so (chapter 2).

## 11.4 Driving the interface from code

The model works without a window. Your script can add elements, run the actions of buttons
and look at the result, which is how you test an interface, and how a script prepares one
before it opens the window. This is the application of section 11.1 again, driven from code:

```python
import liquers as lq

env = lq.Environment()
env.store.set("data/sales.csv", b"region,month,amount\nEU,jan,120\nUS,jan,80\nEU,feb,95\n")

@env.first_command
def dashboard() -> str:
    return """
menu:
  items:
  - !menu
    label: Sales
    items:
    - !button
      label: All sales
      action: "-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child"
    - !button
      label: Europe only
      action: "-R/data/sales.csv/-/ns-rec/to_record/eq-region-EU/q/ns-lui/add-child"
    - !separator
    - !button
      label: Quit
      shortcut: Ctrl+Q
      action: quit
  - !button
    label: Console
    action: "ns-lui/query_console/add-child"
layout: vertical
init:
  - "-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child"
"""

with env.ui() as ui:
    layout = ui.show("dashboard/ns-lui/ui_spec")     # the handle of the new element
    assert ui.wait_idle(timeout=30)                  # wait until nothing is left to evaluate
    assert [(e.type_name, e.parent) for e in ui.elements()] == [
        ("UISpecElement", None),
        ("AssetViewElement", layout),                # the table that the init query added
    ]

    # What the button "Europe only" does:
    ui.submit("-R/data/sales.csv/-/ns-rec/to_record/eq-region-EU/q/ns-lui/add-child", layout)
    assert ui.wait_idle(timeout=30)
    europe = ui.elements()[-1]
    assert europe.parent == layout and str(europe.status) == "Ready"
    assert ui.asset(europe.handle).get().to_dict()["region"] == ["EU", "EU"]

    # Show another query in the same panel.
    ui.show("-R/data/sales.csv/-/ns-rec/to_record/eq-region-US", europe.handle)
    assert ui.wait_idle(timeout=30)
    assert ui.asset(europe.handle).get().to_dict()["amount"] == [80]
env.shutdown()
```

| Call | Does |
|---|---|
| `ui.show(query)` | shows the value of a query in a new element and returns its *handle*, a number. The call returns at once; the query is evaluated in the background |
| `ui.show(query, handle)` | gives an existing element a new query. If the old one is still running, its result is thrown away when it arrives |
| `ui.submit(query, handle)` | runs a query the way a button of that element would, for its effect on the interface |
| `ui.elements()` | what the model holds: for each element its `handle`, `parent`, `type_name`, `title` and `status` |
| `ui.asset(handle)` | the result a element shows, with its log and progress, as chapter 7 describes for any query |
| `ui.wait_idle(timeout)` | waits until every element has finished; `False` when `timeout` seconds pass first |

When the value of the query is a element, as with `ns-lui/ui_spec` and
`ns-lui/query_console`, `show` displays that element. Any other value is shown by the viewer
element, `AssetViewElement`. Components reach Python as `lq.UIElement` objects, with a
`type_name` and a `title`. A command may return one. A element is a live object, not data, so
it cannot be stored.

The `with` block disposes of the model at its end; `ui.dispose()` does the same, and
`env.shutdown()` disposes of every model of the environment. A disposed model refuses every call.

A command that runs from a button can find out which element it was run for:

```python
import liquers as lq

env = lq.Environment()

@env.command
def report() -> str:
    return "rows: 3"

@env.command
def refresh(state, context) -> str:
    return f"refreshed element {context.element}"

with env.ui() as ui:
    handle = ui.show("report")
    ui.submit("refresh", handle)
    assert ui.wait_idle(timeout=10)
env.shutdown()
```

Outside a user interface, `context.element` is `None`. Do not call `wait_idle` or
`await ui.wait_idle_async()` from inside such a command, or any other, `async def` commands
included: the model may be waiting for that very command, so the call raises instead of waiting
forever.

## 11.5 Following what the elements do

Subscribe to status changes with `ui.on("status", callback)`. Each event names the element and its
new status: `Processing` when an evaluation starts, `Ready` or `Error` when it ends.

```python
import liquers as lq

env = lq.Environment()

@env.command
def report() -> str:
    return "rows: 3"

with env.ui() as ui:
    seen = []
    with ui.on("status", lambda event: seen.append((event.handle, str(event.status)))):
        handle = ui.show("report")
        ui.wait_idle(timeout=10)
    assert seen == [(handle, "Processing"), (handle, "Ready")]
env.shutdown()
```

The subscription ends at the end of its `with` block, or when you call its `dispose()`.

Callbacks run only on a thread that asks for them, never at a random moment on a thread of
Liquers: in `wait_idle`, in `await ui.wait_idle_async()` on your event loop, or in
`ui.process_events()`, which delivers what has arrived and returns how many events that was. A
callback may call `show` or `submit` itself. A callback that raises is reported the way Python
reports errors it cannot raise anywhere (`sys.unraisablehook`), and the other callbacks still run.

A query that fails does not raise. Its element shows the error, and the status event says `Error`
and carries the exception as `event.error`. A query that cannot be parsed raises `lq.ParseError`
from `show` at once.

## 11.6 Elsewhere

- **In a notebook**, the values a query returns are ordinary Python objects, and the notebook
  shows them as it shows any other: a `polars.DataFrame`, the `view.to_pandas()` of a record
  view, a PIL image. A rendered template (chapter 10) can be shown as Markdown or HTML.
- **In a web page**, Liquers runs in the browser itself, and a page can also call a Liquers
  server. See [chapter 11 of *Liquers for the Web*](../web/11-ui.md).
- **In a desktop application written in Rust**, see
  [chapter 11 of *Liquers for Rust*](../rust/11-ui.md).

The queries are the same everywhere. A query that you developed in Python can be given to a web
page or to a desktop application unchanged, provided the commands it uses are registered there.

Elements cannot be written in Python yet. A slow query submitted as an action holds up the
model's other work, and freezes an open window, until it ends; keep actions short and let the
elements do the slow work.
