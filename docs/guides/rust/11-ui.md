# 11. User interfaces

PURPOSE: The reader can put together a Liquers user interface from a UI spec and open it in a desktop window, knows how the framework is built and which parts are shared between the desktop and the browser, and knows where the runnable examples are.

Liquers has a small framework for user interfaces whose defining idea is the one of the whole
toolkit: what you see is the value of a query. A panel shows the result of a query, a button
runs a query, and the arrangement of panels is data. The same description then runs in a desktop
window and in a browser page.

This part of Liquers is younger than the rest, and its interfaces will change more. The chapter
starts with a complete small application and then takes its parts one by one. The code blocks
are sketches; the runnable programs are the examples of `liquers-lib`, listed in section 11.6.

## 11.1 A first application

A window with a menu, a table, and a console for trying queries. The application has two
parts. The first is a description of the interface, a *UI spec*, kept in the store as
`ui/dashboard.yaml`:

```yaml
menu:
  items:
  - !menu
    label: Sales
    items:
    - !button
      label: All sales
      action: "-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child"
    - !button
      label: Europe only
      action: "-R/data/sales.csv/-/ns-rec/to_record/eq-region-EU/q/ns-lui/add-child"
    - !separator
    - !button
      label: Quit
      shortcut: Ctrl+Q
      action: quit
  - !button
    label: Console
    action: "ns-lui/query_console/add-child"
layout: vertical
init:
  - "-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child"
```

The second is a program that opens a window on it:

```rust
// Sketch: a desktop program. The runnable versions are the examples ui_query_console_app and
// ui_spec_demo.
use liquers_lib::egui::app::{run_window, WindowCloser, WindowOptions};
use liquers_lib::ui::{app_message_channel, DirectAppState, NativeDriver};

fn main() -> Result<(), Error> {
    let runtime = tokio::runtime::Runtime::new().map_err(|e| Error::general_error(e.to_string()))?;
    let mut driver = runtime.block_on(async {
        let envref = make_environment().to_ref();      // commands, store, recipes
        let app_state = Arc::new(tokio::sync::Mutex::new(DirectAppState::new()));
        let (sender, receiver) = app_message_channel();
        NativeDriver::new(envref, app_state, receiver, sender)
    });
    // The first element: the layout that the UI spec describes.
    driver.ui_context().submit_root_query("-R/ui/dashboard.yaml/-/ns-lui/ui_spec/add-child");
    run_window(WindowOptions::new("Sales"), &mut driver, runtime.handle(), &WindowCloser::default(), None)
}
```

`make_environment` stands for what the earlier chapters built: an environment with the command
library, and a store that holds `data/sales.csv` and the spec. Its evaluations carry a user
interface payload (section 11.3).

Run it, and a window opens that shows the sales table. The menu *Sales* adds the whole table or
the European rows as further panels, and *Console* adds a line in which you can type any query
and see its result.

Nothing in this application draws. The data and the commands are the environment. The
description names a menu, a layout and the queries that fill them. The program opens a window
and submits one query. Everything the user sees is the value of a query: the table is
`-R/data/sales.csv/-/ns-rec/to_record`, and the button *Europe only* shows
`…/to_record/eq-region-EU`. To give the application another view, you register a command and add
one menu item whose action names it.

## 11.2 Describing the interface: the UI spec

Read an action of the menu from the right:

```text
-R/data/sales.csv/-/ns-rec/to_record/q/ns-lui/add-child
```

`ns-lui/add-child` adds an element as a child of the element that started the query, here the
layout that owns the menu. What it adds is the query before it: the instruction `q` turns "the
query so far" into a value instead of evaluating it, so the new element receives the query
`-R/data/sales.csv/-/ns-rec/to_record` as its source and shows its result. The action of
*Console* has no `q`: `ns-lui/query_console` makes an element, and `add-child` adds that element
as it is.

The whole button is therefore data, and so is the dashboard it builds. It can be stored, served
and restored. The queries under `init` run once, when the element first appears.

The spec is read by the command `ns-lui/ui_spec`, which takes the YAML text and returns the
layout element. That is why the program's one query is
`-R/ui/dashboard.yaml/-/ns-lui/ui_spec/add-child`, and why a spec can open another spec. Section
11.8 lists everything a spec may contain, and all commands of `ns-lui`.

## 11.3 The model

Four things make up a user interface.

**The application state** is a tree of *elements*: windows, panels, views. It is the one place
that knows what is on the screen. Each element has a *handle*, a number by which commands refer
to it, and usually a *source*, the query whose value it shows.

**An element** is a value that can draw itself. `liquers-lib` has elements for the common cases:
one that shows the value of an asset with its status and progress, one that lays out children
according to a description, a query console, a Markdown view. An element of your own implements
the trait `UIElement`.

**The runner** connects the tree to the environment. It evaluates the sources of elements that
have none yet, replaces an element when its asset changes, and carries out what elements ask
for.

**The payload** is how a command reaches the user interface. A command cannot touch the screen.
It can, however, receive a payload with the evaluation: a handle to the application state and
the element the query was started from. Commands in the namespace `lui` use it to add, remove
and replace elements. This is the second type parameter of the environment, which has been `()`
throughout this guide:

```rust
// Sketch: an environment whose evaluations carry a user interface payload.
type CommandEnvironment = DefaultEnvironment<Value, SimpleUIPayload>;

let mut builder = default_environment_builder::<Value, SimpleUIPayload>();
liquers_lib::register_all_commands!(&mut builder.command_registry)?; // the library and ns-lui
```

A command that needs something from the payload declares an `injected` argument
(section 5.3). Commands that take a payload are volatile: their effect is on the screen, and it
must happen each time.

## 11.4 On the desktop: egui

With the feature `egui`, elements draw themselves with [egui](https://www.egui.rs). The library
opens the window for you: a *native driver* owns the runner and the application state, and
`run_window` shows it until the window closes, as the program of section 11.1 does.

Call `run_window` on the main thread, outside the runtime: desktop windows must live on the main
thread on some systems, so the library requires it everywhere and returns an error otherwise. It
also returns an error, rather than crashing, when no window can be opened, for instance on a
machine without a display.

egui redraws many times a second, and evaluation is asynchronous. The two meet in the driver: each
frame *ticks* it once, which runs the runner without waiting for any query. An element whose value
is not there yet draws its status and progress, and is replaced when the asset is ready. While
something is evaluating the window keeps repainting, and when nothing is it wakes up a few times a
second.

The window closes when the user closes it, when a *Quit* menu item fires, or when you call
`close()` on the `WindowCloser` from any thread. The last argument of `run_window` is an optional
hook that sees every tick (its status events, a quit request) and can close the window too.

The same driver also runs without a window: `spawn_headless` ticks it on the runtime in the
background, and stopping that task gives the driver back, so a program can move a model between
the background and a window. This is how the Python package drives its user interfaces.

## 11.5 In the browser: the web backend

With the feature `webui`, the same elements produce HTML, and a small runtime keeps the page in
step with the application state. A program compiled to WebAssembly runs the environment, the
runner and the user interface inside the page, with no server.

An element supports the browser by implementing `render_web` next to `show_in_egui`. The
elements of the library have both, which is why a `UISpec` runs unchanged in either place.

There are two ways to get a Liquers user interface into a web page, and they suit different
people. Writing the whole application in Rust and compiling it to WebAssembly is this section.
Loading the ready-made browser module from JavaScript and mounting a user interface into a page
is the subject of *Liquers for the Web*.

## 11.6 The examples

The examples of `liquers-lib` come in pairs, a desktop program and its browser counterpart, in
the folders `liquers-lib/examples` and `liquers-lib/examples-web` of the
[repository](https://github.com/orest-d/liquers):

| Example | Shows |
|---|---|
| `ui_hello` | the smallest complete program: one element that shows the value of a query |
| `ui_spec_simple` | a layout built in code |
| `ui_spec_interactive` | a menu whose buttons add and remove elements |
| `ui_spec_demo` | a dashboard defined in YAML |
| `ui_payload_app` | the payload: commands that change the user interface |
| `ui_button_app` | an element of your own |
| `ui_query_console_app` | a console for typing queries |

```bash
cargo run -p liquers-lib --example ui_spec_demo
```

Start from `ui_payload_app` when you write an application: it has the runner, the payload and
the library's commands in place.

## 11.7 Editing queries

{{> ../_shared/ui-editors.md}}

### In Rust

A window takes the `ui` section through its options, and an editor element can start in either
mode:

```rust
// Sketch: `ui` is the `ui` section, read with serde from your configuration.
let ui: UiConfig = serde_yaml::from_str("mode: system\ndensity: compact\n")?;
run_window(WindowOptions::new("Reports").with_ui(ui), &mut driver, runtime.handle(), &closer, None)?;
let editor = EditorElement::new("Query", kind, binding).with_mode(EditorMode::Advanced);
```

With `mode: system` the window follows the light or dark setting of the desktop while it is open.
A command gets its icon from a hint, `hint icon: "funnel"` after its signature (section 5.2), and
its presets and `next` entries become the chips of its card.

API reference: [`ui::theme`](https://orest-d.github.io/liquers/api/rust/liquers_lib/ui/theme/index.html),
[`ui::editor`](https://orest-d.github.io/liquers/api/rust/liquers_lib/ui/editor/index.html) and
[`WindowOptions`](https://orest-d.github.io/liquers/api/rust/liquers_lib/egui/app/struct.WindowOptions.html) of `liquers_lib`.

## 11.8 Reference: UI specs and `ns-lui`

{{> ../_shared/ui-reference.md}}

In Rust, a UI spec is the type `UISpec` (`UISpec::from_yaml`), and `UISpecElement::from_spec`
makes the element. The words of `add` are resolved by `resolve_position` and
`resolve_navigation` of `liquers_lib::ui`, which a command of your own can call to accept the
same words.

API reference: the module `ui` of [`liquers_lib`](https://orest-d.github.io/liquers/api/rust/liquers_lib/index.html).
