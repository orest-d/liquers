# 11. User interfaces

PURPOSE: The reader knows how a Liquers user interface is put together, which parts are shared between the desktop and the browser, what a UI spec and the `ns-lui` commands offer, and where the runnable examples are.

Liquers has a small framework for user interfaces whose defining idea is the one of the whole
toolkit: what you see is the value of a query. A panel shows the result of a query, a button
runs a query, and the arrangement of panels is data. The same description then runs in a desktop
window and in a browser page.

This part of Liquers is younger than the rest, and its interfaces will change more. This chapter
explains the model and shows its shape. The runnable programs are the examples of `liquers-lib`,
listed in section 11.5.

## 11.1 The model

Four things make up a user interface.

**The application state** is a tree of *elements*: windows, panels, views. It is the one place
that knows what is on the screen. Each element has a *handle*, a number by which commands refer
to it, and usually a *source*, the query whose value it shows.

**An element** is a value that can draw itself. `liquers-lib` has elements for the common cases:
one that shows the value of an asset with its status and progress, one that lays out children
according to a description, a query console, a Markdown view. An element of your own implements
the trait `UIElement`.

**The runner** connects the tree to the environment. It evaluates the sources of elements that
have none yet, replaces an element when its asset changes, and carries out what elements ask
for.

**The payload** is how a command reaches the user interface. A command cannot touch the screen.
It can, however, receive a payload with the evaluation: a handle to the application state and
the element the query was started from. Commands in the namespace `lui` use it to add, remove
and replace elements. This is the second type parameter of the environment, which has been `()`
throughout this guide:

```rust
// Sketch: an environment whose evaluations carry a user interface payload.
type CommandEnvironment = DefaultEnvironment<Value, SimpleUIPayload>;

let mut builder = default_environment_builder::<Value, SimpleUIPayload>();
liquers_lib::register_all_commands!(&mut builder.command_registry)?; // the library and ns-lui
```

A command that needs something from the payload declares an `injected` argument
(section 5.3). Commands that take a payload are volatile: their effect is on the screen, and it
must happen each time.

## 11.2 A user interface as data

The element that lays out children is described by a `UISpec`, which is plain data and has a
YAML form:

```yaml
menu:
  items:
  - !button
    label: Add the sales table
    action:
      query: "sales_table/q/ns-lui/add-child"
  - !button
    label: Show the summary instead
    action:
      query: "summary/q/ns-lui/add-instead"
layout: vertical
init:
  - "sales_table/q/ns-lui/add-child"
```

`sales_table` and `summary` stand for commands of yours. Read the first action from the right.
`ns-lui/add-child` adds an element as a child of the element that started the query. What it
adds is the query before it: the instruction `q` turns "the query so far" into a value instead
of evaluating it, so the new element receives the query `sales_table` as its source and shows
its result. The whole button is therefore data, and so is the dashboard it builds. It can be
stored, served and restored. The queries under `init` run once, when the element first appears.

`ns-lui` has commands to add (`add-child`, `add-instead`, `add-before`, `add-after`), to
`remove`, to move through the tree (`parent`, `children`, `next`, `prev`, `first`, `last`,
`roots`), and to `activate` an element.

## 11.3 On the desktop: egui

With the feature `egui`, elements draw themselves with [egui](https://www.egui.rs), and your
program is an `eframe` application that owns the environment and the application state:

```rust
// Sketch: the frame of an egui application. The runnable version is the example ui_payload_app.
impl eframe::App for MyApp {
    fn ui(&mut self, ui: &mut egui::Ui, _frame: &mut eframe::Frame) {
        // Evaluate what is pending and apply what elements and commands asked for.
        self.runtime.block_on(async {
            if let Err(error) = self.runner.run(&self.app_state).await {
                eprintln!("{error}");
            }
        });
        let roots = match try_sync_lock(self.ui_context.app_state()) {
            Ok(state) => state.roots(),
            Err(_) => return, // busy: draw again in the next frame
        };
        for handle in roots {
            render_element(ui, handle, &self.ui_context);
        }
    }
}
```

egui redraws many times a second, and evaluation is asynchronous. The two meet in the runner: a
frame never waits for a query. An element whose value is not there yet draws its status and
progress, and is replaced when the asset is ready.

Such a program creates its own Tokio runtime and keeps it alive next to the window, because
`eframe` owns the main thread.

## 11.4 In the browser: the web backend

With the feature `webui`, the same elements produce HTML, and a small runtime keeps the page in
step with the application state. A program compiled to WebAssembly runs the environment, the
runner and the user interface inside the page, with no server.

An element supports the browser by implementing `render_web` next to `show_in_egui`. The
elements of the library have both, which is why a `UISpec` runs unchanged in either place.

There are two ways to get a Liquers user interface into a web page, and they suit different
people. Writing the whole application in Rust and compiling it to WebAssembly is this section.
Loading the ready-made browser module from JavaScript and mounting a user interface into a page
is the subject of *Liquers for the Web*.

## 11.5 The examples

The examples of `liquers-lib` come in pairs, a desktop program and its browser counterpart, in
the folders `liquers-lib/examples` and `liquers-lib/examples-web` of the
[repository](https://github.com/orest-d/liquers):

| Example | Shows |
|---|---|
| `ui_hello` | the smallest complete program: one element that shows the value of a query |
| `ui_spec_simple` | a layout built in code |
| `ui_spec_interactive` | a menu whose buttons add and remove elements |
| `ui_spec_demo` | a dashboard defined in YAML |
| `ui_payload_app` | the payload: commands that change the user interface |
| `ui_button_app` | an element of your own |
| `ui_query_console_app` | a console for typing queries |

```bash
cargo run -p liquers-lib --example ui_spec_demo
```

Start from `ui_payload_app` when you write an application: it has the runner, the payload and
the library's commands in place.

In Rust, a UI spec is the type `UISpec` (`UISpec::from_yaml`), and `UISpecElement::from_spec`
makes the element. The words of `add` are resolved by `resolve_position` and
`resolve_navigation` of `liquers_lib::ui`, which a command of your own can call to accept the
same words.
