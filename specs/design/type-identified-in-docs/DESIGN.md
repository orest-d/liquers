# The documents say that no type implements TypeIdentifiedIn yet

Bulk design (`specs/guides/autonomous_bulk_design.md`), 2026-10-26: Phases 1-4 written; Phase 4
implemented on 2026-10-27 (automatic fix).

## Phase 1: High-Level Design

### Purpose

`TYPE_SYSTEM_GUIDE.md` tells a reader to derive an identifier with
`to_type_identifier::<ExtValue, polars::frame::DataFrame>()`, which does not compile: nothing
implements `TypeIdentifiedIn` (`liquers-core/src/type_system.rs`). The implementations are the
generated output of `value-type-definition-macro` (its Phase 2 item 6), an `XL` design awaiting
decisions. Until it lands, the documents must say what exists, so a reader is not sent to a
trait-bound error.

### Problem Example

Verified at HEAD: `grep -rn "TypeIdentifiedIn" --include=*.rs` finds only the definition and the
`Arc<T>` / `&T` blanket impls. A reader follows `specs/guides/TYPE_SYSTEM_GUIDE.md` §"Naming a type
in Rust code":

```rust
let id = to_type_identifier::<ExtValue, polars::frame::DataFrame>();   // guide: "polars.DataFrame"
```

Today: `error[E0277]: the trait bound DataFrame: TypeIdentifiedIn<ExtValue> is not satisfied`.
Should be: the guide says the bridge is defined but not yet implemented for any type, names the
design that will generate the impls, and tells the reader what to use meanwhile (the value's
`identifier()` / the `TypeInfo` in `type_descriptions()`).

### Scope and Acceptance Criteria

- **AC-1** The guide example is not presented as working
  WHEN `TYPE_SYSTEM_GUIDE.md` §"Naming a type in Rust code" is read
  THEN it states that no type implements `TypeIdentifiedIn` yet, names
  `design/value-type-definition-macro/` as the producer, and gives the interim way to obtain an
  identifier
- **AC-2** The reference states the current state
  WHEN `VALUE_TYPE_SYSTEM.md` §"Rust types and identifiers" is read
  THEN it says the trait and its blanket impls exist, and that no value type implements it at HEAD
- **AC-3** The rustdoc agrees
  WHEN the documentation of `TypeIdentifiedIn` in `liquers-core/src/type_system.rs` is read
  THEN it carries the same one-sentence status, and `cargo test -p liquers-core --doc type_system`
  still passes (the existing example stays `ignore`)

Non-goals: writing the impls by hand (they are step 6 of the macro design, which would replace
them); argument typing at command registration (`COMMAND-INPUT-OUTPUT-TYPES-ARE-UNDECLARED`).

### Design Readiness

- **Readiness:** ready
- **Automatic fixing:** eligible — a documentation fix in two `specs/` documents and one rustdoc
  comment in `liquers-core`; no code, signature or format change.
- **Leading issue:** None.
- **Explanation:** the issue offers two remedies; hand-written impls now would be generated over by
  `value-type-definition-macro` and need registry-agreement tests of their own, while the documents
  are wrong today. The status sentences are removed by that design when it lands.
- **Open questions:** None. The "implement by hand now" alternative is recorded as rejected in
  Phase 2; a maintainer who wants the bridge before the macro can file it as its own feature.

### Design Dependencies

- `value-type-definition-macro` — **covered-by** for the implementations (its AC-5, test
  `rust_types_name_their_identifiers`); this design covers only the documents until then. When the
  macro lands it removes the status sentences added here (a line for its Phase 4 document step).
- `value-conversion-registry` — **overlaps**, weak: assumes the bridge for automatic conversion;
  unaffected by a documentation change.

### Consolidated Findings

- The reference already describes the trait correctly; only "in use" is implied. The guide's
  example is the defect.
- The rustdoc example is `ignore`, so no doctest is broken today.

## Phase 2: Architecture

### Solution

Three text edits, no code:

1. `specs/guides/TYPE_SYSTEM_GUIDE.md` §"Naming a type in Rust code": keep the example as the
   intended form, preceded by: "**Not yet available.** `TypeIdentifiedIn` is defined in
   `liquers-core` but no value type implements it; the implementations are generated by
   `define_value_types!` (`design/value-type-definition-macro/`). Until then, take the identifier
   from a value (`value.identifier()`) or from its `TypeInfo` in `type_descriptions()`."
   History row and `reviewed:` bump (§9.2).
2. `specs/reference/VALUE_TYPE_SYSTEM.md` §"Rust types and identifiers": one sentence after the code
   block — "At HEAD no value type implements `TypeIdentifiedIn`; only the `Arc<T>` and `&T` blanket
   impls exist." History row and `reviewed:`.
3. `liquers-core/src/type_system.rs`, rustdoc of `TypeIdentifiedIn`: the same status sentence.

Rejected: implement `TypeIdentifiedIn<ExtValue>` (and `<CombinedValue<B, ExtValue>>`) by hand for
`image::DynamicImage`, `polars::frame::DataFrame` and the record traits now — a new public surface
that the macro design regenerates, plus core `Value` payload impls nobody consumes yet.

Known-issue preflight: nothing blocks.
