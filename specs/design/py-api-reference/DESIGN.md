# Every public name of the Python package has a docstring, and a script generates its API reference

Bulk design (`specs/guides/autonomous_bulk_design.md`), 2026-10-27: Phases 1-4 written, not
approved, nothing implemented.

## Phase 1: High-Level Design

### Purpose

`liquers` is mostly PyO3 classes whose methods carry no `///` comment, so `help()`, editors and
agents see bare names, and nothing generates a per-method reference. This design documents every
public name, adds the check the language-integration guide asks for (`DOCS04`), and adds a script
that builds an HTML API reference from the docstrings. It serves `VISION.md`'s "Python data
science" use case and its "Better Python integration" priority.

### Problem Example

```python
help(lq.Query)              # method names only, no descriptions
lq.Query.encode.__doc__     # None
lq.KeyNotFoundError.__doc__ # None (generated by liquers/_errors.py `_install`)
```

Verified at HEAD (`04667a80`) by a source scan (heuristic: a `///` line directly above the item or
its attributes; `#[new]`, `#[setter]`, dunder and `_`-prefixed items not counted):

| Kind | Public | Without a docstring |
|---|---|---|
| Registered classes (`liquers-py/src/lib.rs` `_native`) | 45 | 40 (all but `Environment`, `Issue`, `Context`, `State`, `AssetRef`) |
| Their public methods and properties | 285 | 238 (`MetadataRecord` 53, `AssetInfo` 25, `Metadata` 22, `Query` 19, …) |
| Native functions (`parse`, `parse_key`, `build_plan`) | 3 | 3 |
| Generated error classes (27 variants, 3 categories) | 30 | 30 |
| Python-level names (`command`, `evaluate`, `LiquersError`, …) | 6 | 0 |

About 311 of 369 names; the issue's runtime count on 2026-10-19 was 285 of 392 (a different
counting rule). No `text_signature` attribute exists in `liquers-py/src/` (one `signature`, in
`query.rs`). No generator configuration or docs script exists; `scripts/` has
`test-liquers-py.sh`, which already pip-installs `maturin pytest polars pillow`.

### Scope and Acceptance Criteria

- **AC-1** Every public name is documented
  WHEN the coverage test walks `lq.__all__` and each listed class's own public attributes
  THEN every one has a non-empty `__doc__`
- **AC-2** Coverage cannot regress
  WHEN a public method or class without a docstring is added
  THEN the coverage test fails and names it
- **AC-3** Every public callable has a signature
  WHEN `inspect.signature` is applied to each public function and method
  THEN it does not raise
- **AC-4** An HTML API reference is generated
  WHEN `bash scripts/build-liquers-py-docs.sh` runs
  THEN it writes an HTML reference under `target/liquers-py-docs/` that lists every name in
  `lq.__all__`
- **AC-5** The test loop builds it
  WHEN `bash scripts/test-liquers-py.sh` runs and the generator fails on a docstring
  THEN the script fails

Non-goals: type stubs (`.pyi`, `py.typed`, the guide's `STUBS` feature); publishing the reference
(`PACKAGE`); renaming or reshaping any API (`py-metadata-fields-as-properties`); moving the guide
to `docs/`.

### Design Readiness

- **Readiness:** needs-decision
- **Automatic fixing:** not-eligible — the generator is a new (development) dependency installed
  by a script, chosen between two tools (rule 4, and rule 5 until question 1 is decided). The
  docstring and coverage-test part alone (AC-1 to AC-3, steps 1-6) would be eligible: doc comments
  plus a new test, size `M`, one crate (`liquers-py`), no structure or interface change. See
  question 3.
- **Leading issue:** question 1.
- **Explanation:** writing the docstrings and the check needs no decision; only the generator
  does, and either tool reads the same docstrings.
- **Open questions:**
  1. **Open design - generator:** `pdoc` (recommended): no configuration file, reads `__doc__` and
     `__text_signature__` of an extension module, renders Markdown (the backtick style the
     existing docstrings use), one command. Sphinx `autodoc`: needs `conf.py` and reStructuredText,
     worth it only if the reference is to join other Sphinx documents, which none are.
  2. **Proposed resolution - output and publication:** generated into `target/liquers-py-docs/`,
     never committed (a generated copy drifts); publishing waits for `PACKAGE`.
  3. **Proposed resolution - split:** implement steps 1-6 first as an automatic fix (they stand
     alone and close AC-1 to AC-3), and steps 7-9 after question 1. The maintainer decides whether
     to split the issue; this design keeps both parts.
  4. **Implementation detail - docstring style:** a one-line summary in the Python reader's terms
     (no Rust paths), then arguments, result and raised errors in prose; links to the guide by
     section.

### Design Dependencies

- `language-binding-tests-in-ci` — **overlaps**: once CI runs `scripts/test-liquers-py.sh`, AC-5
  runs there too and CI needs `pdoc` installed by that script. No order.
- `py-metadata-fields-as-properties`, `py-metadata-typed-errors`, `py-python-style-reprs` —
  **overlaps**: they edit the same `#[pymethods]` blocks (`metadata.rs`, `recipes.rs`,
  `expiration.rs`, `__repr__`s). T3 was considered and rejected: a `///` line is independent of a
  `#[getter]` or an error-mapping change, and conflicts are line-level; whichever lands second
  rebases. `__repr__` is a dunder and not in the coverage set.
- `py-command-decorator-declaration-keywords` — **overlaps**: its new keywords and `realm`
  parameters are documented by whichever lands second; AC-1 catches an omission.

### Consolidated Findings

- PyO3 turns a `///` comment on a `#[pyclass]` or `#[pymethods]` item into `__doc__`; a property's
  doc comes from its `#[getter]`. Classes generated with `type()` in `_errors.py` have no `__doc__`
  unless `_install` passes one.
- The existing `///` comments on public items were written for Rust readers (e.g. "Called by the
  decorators in `liquers._commands`" is on the private `_register_command`); public ones are
  reviewed for a Python reader in the same pass.
- The coverage set is defined as the issue does (`__all__` plus each class's own public
  attributes); enum members are instances of their class and are skipped.
- The Python suite is not in CI yet (`PY-TESTS-NOT-RUN-IN-CI`).

## Phase 2: Architecture

### Solution

1. **Docstrings.** Add a `///` comment to every registered `#[pyclass]`, every public
   `#[pymethods]` item (getters included) and the three `#[pyfunction]`s in
   `liquers-py/src/{query,command_metadata,metadata,error,expiration,dependencies,plan,recipes,environment,context,asset}.rs`.
   Where `inspect.signature` raises, add `#[pyo3(text_signature = "(…)")]` (PyO3 generates one
   for most functions and methods; the AC-3 test finds the rest).
2. **Generated error classes.** `liquers-py/python/liquers/_errors.py` `_install` passes
   `"__doc__"` in the namespace of each generated class: "Raised for `ErrorType.<Variant>`." for a
   variant and "Base class of every error in the <category> category." for a category.
3. **Coverage test.** `liquers-py/tests/test_DOCS_api_reference.py`, the guide's `DOCS04`
   blueprint (`LANGUAGE-INTEGRATION_GUIDE.md` Appendix A §DOCS) extended to class attributes.
4. **Generator.** `scripts/build-liquers-py-docs.sh`: reuses the venv layout of
   `test-liquers-py.sh` (or takes `VIRTUAL_ENV`), `pip install pdoc`, then
   `python3 -m pdoc liquers -o target/liquers-py-docs`, exiting non-zero on failure.
   `scripts/test-liquers-py.sh` calls it after pytest.

Rejected: a hand-written per-method reference in `specs/` (the issue rules it out; it drifts); a
docstring-coverage tool such as `interrogate` (reads source files, so it cannot see a PyO3
extension's `__doc__`).

### Changes

- `liquers-py/src/*.rs`: comments and, where needed, `text_signature` attributes only. No
  signature, type or behaviour change.
- `liquers-py/python/liquers/_errors.py` `_install`.
- New `liquers-py/tests/test_DOCS_api_reference.py`, new `scripts/build-liquers-py-docs.sh`,
  `scripts/test-liquers-py.sh` (one call and its header comment).
- Documents: `liquers-py/README.md` "Building and testing" (the docs script; `pdoc` among the
  installed packages) and `DOCS` row (`DOCS04` passes); `specs/reference/PYTHON_INTEGRATION.md` §8
  limitation removed; `specs/guides/PYTHON_GUIDE.md` §1 (how to build the reference) and §10;
  `specs/reference/api/API_DOCS_GAP_ANALYSIS.md` DOC-12 row. History rows and `reviewed:` bumps.

### Risks

| Risk | Mitigation | Certainty |
|---|---|---|
| A `text_signature` that does not match the real parameters | AC-3 checks it parses; review compares with `#[pyo3(signature)]` | medium |
| Docstrings repeat the guide and drift | one-line summaries plus a link to the guide section for semantics | medium |
| `pdoc` fails on an extension module or a free-threaded build | test on CPython 3.13 and 3.14t, as the suite does; Sphinx is the fallback | medium |
| A long diff conflicts with the overlapping designs | comment-only lines; whichever lands second rebases | high |
| Network needed for `pip install pdoc` | the test script already installs from pip | high |

Recovery: revert; comments and a new test file change no behaviour.

## Phase 3: Examples and Tests

### Examples

After the change, `lq.Query.encode.__doc__` is a sentence ("The query as text, in the encoded
form `parse` reads back."), `help(lq.Query)` lists each method with its signature and summary, and
`target/liquers-py-docs/liquers.html` has a section per class.

### Tests

In `liquers-py/tests/test_DOCS_api_reference.py`:

- `test_DOCS04_every_public_name_is_documented` — every name in the coverage set has a non-empty
  `__doc__`; the failure message lists the missing ones: AC-1, AC-2
- `test_DOCS04_every_public_callable_has_a_signature` — `inspect.signature` on every function and
  method in the set: AC-3
- `test_DOCS04_api_reference_lists_every_public_name` — `pytest.importorskip("pdoc")`, runs
  `python3 -m pdoc liquers -o <tmp_path>`, and checks the output names each `__all__` entry: AC-4

AC-5 is checked by running `scripts/test-liquers-py.sh` with one docstring temporarily broken for
the generator (a step-9 check, reverted). Run: `bash scripts/test-liquers-py.sh -k DOCS04`, and
`bash scripts/build-liquers-py-docs.sh`.
